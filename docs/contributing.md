# Contributing

This guide covers the commit convention, the local pre-commit hooks, and the
pull-request flow for this firmware. To build, see
[docs/build-from-source.md](build-from-source.md); for the firmware module map
and ranging-data flow, see [docs/architecture.md](architecture.md).

## Commit convention

Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/)
in the form `type(scope): summary` — lowercase type, imperative mood, no trailing
period. The scope is optional and rarely used; the only recurring scope is `version`,
on the automated `chore(version): vX.Y.Z` bump commit. The types in use are `feat`,
`fix`, `docs`, `ci`, `chore`, and `style` (the standard `refactor`, `perf`, `test`,
`build`, and `revert` are also valid). Examples:

- `feat: add install codifier + onboarding-verification CI`
- `docs: add architecture overview for the firmware`
- `fix: add trailing newline to architecture.md`

The convention is backed by [cocogitto](https://docs.cocogitto.io/), configured in
[cog.toml](../cog.toml). Two things follow from that config: the `chore`, `ci`, and
`test` types are `omit_from_changelog = true` and never appear in the changelog; and
`CHANGELOG.md` is regenerated by `cog bump --auto` during the automated release flow
in [.github/workflows/release.yml](../.github/workflows/release.yml). **Do not edit
`CHANGELOG.md` by hand** — it is regenerated on each release and is excluded from the
pre-commit hooks for the same reason.

There is **no** local `commit-msg` hook and **no** `cog check` step in CI, so a
non-conforming message is not caught until review. `cog bump --auto` is **not** a
backstop here: it silently ignores any subject that fails Conventional Commits
parsing, so a bad subject alongside a conventional one still releases — only
`cog check` validates subjects, and that is not in CI. Review is the sole
enforcement.

## Pre-commit hooks

Install the hooks once per clone (requires Python):

```bash
pip install pre-commit
pre-commit install
```

From then on the hooks run on `git commit`. To check the whole tree at any time, run
`pre-commit run --all-files`; to check only staged files, run `pre-commit run`. The
hook set is defined in [.pre-commit-config.yaml](../.pre-commit-config.yaml), which
excludes `.vscode/` and `CHANGELOG.md` from every hook and sets no `stages`, so all
hooks run at the pre-commit stage. The hooks are:

| Hook | Repo (rev) | Checks |
|------|------------|--------|
| `trailing-whitespace` | pre-commit-hooks v6.0.0 | strips trailing whitespace |
| `end-of-file-fixer` | pre-commit-hooks v6.0.0 | ensures a final trailing newline |
| `check-yaml --unsafe` | pre-commit-hooks v6.0.0 | parses YAML |
| `check-json` | pre-commit-hooks v6.0.0 | parses JSON |
| `check-added-large-files --maxkb=2000` | pre-commit-hooks v6.0.0 | blocks files > 2 MB |
| `mixed-line-ending --fix=lf` | pre-commit-hooks v6.0.0 | normalizes to LF |
| `typos` | crate-ci/typos v1.47.2 | spell checker (config: [typos.toml](../typos.toml)) — **not** codespell |
| `clang-format` | mirrors-clang-format v22.1.5 | C formatter, `types: [c]` only (config: [.clang-format](../.clang-format)) |
| `cmake-format` | cheshirekow/cmake-format-precommit v0.6.13 | CMake formatter (no config file; built-in defaults) |

Domain terms live in an allowlist in [typos.toml](../typos.toml) (`HCI`,
`nrf54lm20`, `COBS`, `serde`, and the like). When you add a legitimate project
term that `typos` flags, extend that allowlist rather than disabling the hook.

The `end-of-file-fixer` hook is the reason every committed file — this guide
included — must end with exactly one trailing newline.

## Pull-request flow

Pull requests target `main` (the only branch `cog bump --auto` runs on, per
[cog.toml](../cog.toml); `ci.yml` triggers on every `pull_request` with no branch
filter). Every PR runs all jobs in
[.github/workflows/ci.yml](../.github/workflows/ci.yml). All must be green:

- `verify-ncs-version` (ubuntu-latest) — runs `scripts/check-ncs-version.sh` to
  assert every live NCS version literal agrees with `west.yml`'s `nrf` revision.
  Default-branch pushes also check the `vars.NCS_VERSION` repo variable. See the
  NCS version management section below.
- `lint` (ubuntu-latest) — `pre-commit/action@v3.0.1` runs
  `pre-commit run --all-files`. This is the only place the hooks above are enforced.
- `detect-presets` (ubuntu-latest) — reports whether either role has build
  presets. The build jobs below consume its output and are skipped only when a
  role has no presets defined.
- `build-initiator` (NCS v3.4.1 container) — `ci/build.sh --target initiator`
  over every preset in `initiator/CMakePresets.json`.
- `build-reflector` (same container) — `ci/build.sh --target reflector` over
  every preset in `reflector/CMakePresets.json`.
- `onboarding-verification` (clean `ubuntu:24.04`) — runs
  `scripts/install-toolchain.sh --with-rust` then builds **both** the reflector and
  the initiator (the latter exercising the Rust COBS-serializer bridge), guarding the
  documented native install path for both firmware variants.

The `Docs` workflow
([.github/workflows/docs.yml](../.github/workflows/docs.yml)) also gates every
`pull_request` and every push to `main`. It validates the internal inline
links between the [README](../README.md) and the guides in `docs/` (this one
included), so a renamed or moved guide is caught before a user hits a dead
link; confirms the release-artifact name in
[docs/flash-quickstart.md](flash-quickstart.md) matches the archive
[release.yml](../.github/workflows/release.yml) produces; cross-checks the
preset names in the docs table against the `configurePresets` in
`initiator/CMakePresets.json` and `reflector/CMakePresets.json`; and confirms
[docs/flash-quickstart.md](flash-quickstart.md) names every image the preset
enumeration puts in the release archive. Run it locally with
`bash scripts/check-docs.sh`.

There is no `.github/pull_request_template.md`, no `CODEOWNERS`, and no in-repo
branch-protection hint — a PR is simply a branch opened against `main` with all
checks green. To avoid a red `lint` job, run `pre-commit run --all-files` before
pushing; to pre-empt the build jobs, reproduce them locally with the two
`ci/build.sh` commands above (see
[docs/build-from-source.md](build-from-source.md) for toolchain setup).

## Adding a board

The board-support contract is documented in
[boards/README.md](../boards/README.md) and
[docs/hardware.md](hardware.md#board-support-contract). In short: overlay,
optional board `.conf`, presets, and docs rows. The nRF54LM20-DK is the first
board added under this contract — use its overlay and preset entries as the
reference. CI and the release workflow pick up new presets automatically
through `ci/list-presets.sh` — there are no hand-maintained preset lists to
update.

## NCS version management

The NCS version has one source of truth: `west.yml`'s `nrf` project `revision`
(e.g. `v3.4.0`). A GitHub repo variable, `vars.NCS_VERSION`, carries that version
into the CI workflows where GitHub Actions expressions need it at job startup
(container image tags and cache keys in `ci.yml` / `release.yml` evaluate
`${{ vars.NCS_VERSION }}` — they cannot read `west.yml` at evaluation time).

A shared scanner (`scripts/ncs-version-lib.sh`) defines what counts as an NCS
version reference and is used by two scripts:

- `scripts/check-ncs-version.sh` — the guard. Verifies every NCS literal in the
  repo (README, live docs, scripts, container tags, cache keys) agrees with
  `west.yml`, and on default-branch CI also that `vars.NCS_VERSION` agrees with
  it. Archived release notes, decision records, and captured boot banners stay
  as historical records. Fails loudly on a stale live literal, a
  mismatched variable, or an unset variable (which would otherwise produce an
  opaque tagless container image). Run locally with
  `bash scripts/check-ncs-version.sh`.
- `scripts/bump-ncs.sh <version>` — the bump operation. The single way to move
  the NCS version: checks the clean default branch, upstream tag, and toolchain
  image; rewrites `west.yml` and every live literal the scanner finds; runs the
  guard as a self-check; and opens a PR. Use `--dry-run` to preview rewrites
  locally without opening a PR. The script never changes `vars.NCS_VERSION`.

Before proposing a bump, read both the target SDK release notes and the
radio-stack library changelogs for changes that affect channel sounding,
Bluetooth, USB, or the toolchain. The v3.4.2 and v3.5.0 upgrade decisions are
deferred; this machinery repair does not choose either version.

Immediately before merging the bump PR, set `vars.NCS_VERSION` to its proposed
`west.yml` revision. Do not merge another PR in that window. The release
workflow selects its toolchain image using that variable before it checks out
the manifest, so it must be ready for the merge. Pull-request CI scans the
proposed files but does not compare the variable while the PR is open. Use a
`fix:` bump commit so the release tool cuts a patch release on merge.
For the v3.4.1 bump, pass `--reason-file PATH` with a body naming DRGN-29129,
DRGN-29277, DRGN-29459, and DRGN-29669 so the commit and release notes
explain the SDK change.

**One-time bootstrap:** before this mechanism goes live (or after cloning for CI),
set the repo variable to the current `west.yml` revision:

```
gh variable set NCS_VERSION v3.4.1
```

Maintainers update the variable immediately before each bump merges.

## Out of scope

- Editing `CHANGELOG.md` (auto-generated by `cog bump --auto`) and cutting releases
  manually (automated by `release.yml` on push to `main` — a `feat:` merge triggers a
  minor-version bump).
- A pull-request template, issue templates, `CODEOWNERS`, or branch-protection rules
  (none exist, and none are added by this guide).
- A generated documentation site.
- The COBS wire format and the `mars-bluetooth-hci` API (see
  [docs/architecture.md](architecture.md)).
- The board / preset / fragment table (see [docs/hardware.md](hardware.md)).
